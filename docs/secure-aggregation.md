# 🛡️ Secure Aggregation

## Motivation

Federated Learning keeps raw training data on the clients, but this alone does not guarantee privacy.

Without additional protection, the aggregation server can receive the individual model updates generated by each client.

A server following the FL protocol correctly may still inspect these individual updates and attempt to infer information about the client's local training data.

This project experimentally demonstrates this threat using an **honest-but-curious server**.

## Threat Model

The honest-but-curious server is assumed to:

* follow the federated-learning protocol correctly;
* perform the aggregation as expected;
* receive individual client updates;
* inspect those updates to extract information about local data.

The server is therefore not assumed to modify the training protocol.

Its malicious behavior consists of **observing and analyzing information that is available to it**.

## Attack Without Secure Aggregation

Without Secure Aggregation, the server can observe individual client parameters.

The project records the six model tensors:

```text
fc1.weight
fc1.bias

fc2.weight
fc2.bias

fc3.weight
fc3.bias
```

The recorded updates can then be analyzed across training rounds.

The experimental environment generated individual-update logs for **30 rounds**.

## Honest-but-Curious Analysis

The project includes an analysis of individual client updates using:

* L2 norms
* mean and standard deviation
* client distance matrices
* final-layer deviation analysis

The objective is to determine whether the server can distinguish the local behavior of different clients.

## Property Inference

A dedicated property-inference experiment analyzes the final layer of the client models.

The attack uses deviations in the model parameters to infer properties of the local training data.

The experiment successfully reconstructed information about the local classes represented on individual clients.

This demonstrates that:

> **mTLS protects model updates while they are transmitted, but does not by itself prevent an aggregation server from inspecting updates after they reach the server endpoint.**

## Secure Aggregation

To mitigate this leakage, the project integrates **Secure Aggregation (SecAgg+)**.

The implemented protocol uses pairwise masking.

Conceptually:

```text
Client 1 ──┐
           │ masked update
Client 2 ──┼──────────────► Aggregation
           │
Client 3 ──┘
```

The individual client contributions are masked before aggregation.

The server receives the combined protected contribution rather than directly observing each individual update.

## Pairwise Masking

The implementation uses pairwise shared secrets between clients.

Conceptually, for clients `i` and `j`:

```text
sij = sji
```

The shared secrets are used to derive masks.

The masks are added with opposite signs for the two clients so that they cancel when the server aggregates all client contributions.

The resulting aggregation retains the intended global update while preventing the server from isolating an individual client's contribution.

## SecAgg+ Integration

The project implements the Secure Aggregation logic in:

```text
secagg.py
```

The module was validated with a dedicated unit test and then integrated into the live FL environment.

Secure Aggregation can be enabled through:

```text
SECAGG=1
```

The live execution confirms that the client-side parameters are masked before transmission.

## Before vs After

### Without Secure Aggregation

```text
Client 1 ─────────►
Client 2 ─────────►  FL Server
Client 3 ─────────►

Server sees:
  Client 1 update
  Client 2 update
  Client 3 update

        ↓
Weight analysis
        ↓
Property inference
        ↓
Local information leakage
```

### With Secure Aggregation

```text
Client 1 ──► Mask ──┐
Client 2 ──► Mask ──┼──► FL Server
Client 3 ──► Mask ──┘

Server sees:
      Aggregated result

Individual contributions
are not directly exposed.
```

## Replay Validation

After integrating SecAgg+, the previously demonstrated attacks were replayed.

The experiments compared the situation without masking against the protected configuration.

The report confirms that, after masking, the previous direct information leakage from individual client updates was neutralized.

## Convergence Considerations

Secure Aggregation introduced an additional practical consideration during live training.

The report indicates that convergence with masking required a correction to the aggregation behavior: a uniform average of `1/N` was used to avoid an F1 collapse caused by the interaction with the masking mechanism.

The report also identifies an extended Secure Aggregation training campaign as future work.

Therefore, Secure Aggregation is considered successfully integrated and validated from a privacy perspective, while further experiments are still required to fully characterize its impact on federated convergence.

## Security Conclusion

The experiment demonstrates an important distinction:

```text
mTLS
 │
 └── protects communication in transit

Secure Aggregation
 │
 └── protects individual client contributions
     from the aggregation server
```

The two mechanisms therefore address different parts of the threat model and are complementary rather than interchangeable.
