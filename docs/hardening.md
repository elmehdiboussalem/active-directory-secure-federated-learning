# Active Directory Attack Assessment

## Overview

The project includes a controlled security assessment of the `nord.corp` Active Directory environment.

The objective was to reproduce representative Active Directory attack techniques, observe the Windows telemetry generated by each attack, apply a corresponding hardening measure, and replay the scenario to verify that the attack was no longer effective.

This assessment also provides the operational link between the federated intrusion-detection model and the threats it is designed to recognize.

The tested attack chain follows a realistic progression:

```text
Reconnaissance
      │
      ▼
Credential / Ticket Exposure
      │
      ▼
Offline Secret Recovery
      │
      ▼
Lateral Movement
      │
      ▼
Domain Secret Extraction
      │
      ▼
Persistence
```

All experiments were performed inside the isolated project laboratory.

---

## Laboratory Environment

The offensive scenarios were executed from a Kali Linux workstation against the `nord.corp` domain.

The laboratory deliberately contained controlled weaknesses, including:

* a service account configured without Kerberos pre-authentication;
* service accounts exposing SPNs;
* controlled NTLM exposure;
* LLMNR/NBT-NS enabled during the initial test;
* an intentionally exposed AD CS web enrollment configuration.

Windows auditing was enabled so that the attacks generated the event telemetry consumed by the detection pipeline.

The assessment followed the same process for each technique:

```text
Attack
  │
  ▼
Observation
  │
  ▼
Hardening
  │
  ▼
Replay
  │
  ▼
Verification
```

# 1. BloodHound Reconnaissance

## Objective

BloodHound was used to map relationships inside the Active Directory environment and identify potential paths toward privileged accounts.

The collection exposed relationships such as:

* group memberships;
* ACL relationships;
* session information;
* privileged-account paths.

The resulting graph was used to identify unnecessary privileges and short attack paths.

---

## Hardening

The project reduced the reconnaissance surface through several measures:

### Session enumeration

Remote session enumeration was restricted using the `SrvsvcSessionInfo` security configuration.

This prevents standard users from freely enumerating who is logged on to which systems.

### Remote SAM-R enumeration

`RestrictRemoteSAM` was configured so that only administrators could perform the relevant remote SAM queries.

### Excessive ACL removal

Dangerous permissions such as unnecessary `GenericAll` and `WriteDACL` relationships were removed from the environment.

### Detection

Large volumes of LDAP directory-read activity were identified as a useful reconnaissance signal.

---

## Result

After hardening, the information available to an unprivileged reconnaissance account was reduced, limiting the attack graph exposed to BloodHound.

The project therefore treats directory reconnaissance as an attack stage rather than assuming that authentication alone is sufficient protection.

# 2. AS-REP Roasting

**MITRE ATT&CK: T1558.004**

## Principle

AS-REP Roasting targets accounts for which Kerberos pre-authentication is disabled.

A deliberately vulnerable service account, `svc_legacy`, was created for the laboratory with the `DONT_REQ_PREAUTH` condition.

The attacker could request an AS-REP response without first proving knowledge of the account password. The resulting material could then be subjected to offline password recovery.

---

## Hardening

The remediation addressed both the configuration weakness and password strength:

* Kerberos pre-authentication was re-enabled;
* the vulnerable account received a new strong password;
* the domain password policy was strengthened;
* the domain was audited for remaining accounts with pre-authentication disabled.

The reported password-policy configuration included:

* minimum length: 14 characters;
* complexity enabled;
* password history: 24;
* maximum password age: 90 days;
* lockout after 5 failed attempts.

---

## Verification

A domain-wide search confirmed that no remaining accounts had the vulnerable `DoesNotRequirePreAuth` configuration.

The final AS-REP enumeration test returned no roastable entries.

Therefore:

```text
Before hardening  → vulnerable account found
After hardening   → no roastable account found
```

The attack was considered neutralized in the laboratory.

# 3. Kerberoasting

**MITRE ATT&CK: T1558.003**

## Principle

Kerberoasting targets service accounts associated with Service Principal Names (SPNs).

The laboratory used controlled service accounts including:

```text
svc_sql
svc_http
```

with SPNs configured for the initial attack scenario.

An authenticated user could request service tickets for these accounts. The resulting ticket material could then be subjected to offline password recovery.

The corresponding Kerberos activity was also visible in domain-controller telemetry and therefore provided a useful signal for the detection system.

---

## Hardening

Three defensive principles were applied:

1. Strengthen service-account secrets.
2. Prefer modern Kerberos encryption.
3. Remove unnecessary SPNs.

The laboratory configuration included:

* AES128/AES256 support;
* `msDS-SupportedEncryptionTypes = 24`;
* stronger service-account secrets;
* a KDS root key;
* migration toward a gMSA;
* removal of the exposed SPN where it was no longer required.

The gMSA configuration provides automatically managed credentials rather than relying on manually maintained service-account passwords.

---

## Verification

The hardened environment produced AES-256 ticket material instead of the original RC4-based material.

The reported offline cracking test did not recover the AES-protected secret during the observed test period.

The exposed SPN was also removed, and subsequent service-principal enumeration returned no vulnerable entry.

Finally, authentication attempts using the former service-account credentials failed.

Therefore:

```text
SPN exposure
     │
     ▼
Service ticket
     │
     ▼
Offline attack
```

was replaced by:

```text
Minimal SPN exposure
        +
AES
        +
Strong / managed credentials
        │
        ▼
Reduced Kerberoasting risk
```

# 4. Pass-the-Hash

**MITRE ATT&CK: T1550.002**

## Principle

Pass-the-Hash abuses an NTLM credential material extracted from a compromised system.

The laboratory reproduced the scenario by testing controlled extraction of NTLM secrets and subsequent authentication attempts using the captured hash rather than the original password.

This demonstrated the relationship between credential exposure and lateral movement.

---

## Hardening

The project deployed several complementary controls.

### LSASS protection

`RunAsPPL` was enabled so that LSASS runs as a protected process.

### Credential Guard

Credential Guard and virtualization-based security were enabled to isolate sensitive authentication material.

### NTLMv2-only configuration

The LAN Manager authentication level was configured to use NTLMv2 and reject older LM/NTLM authentication.

### NTLM restriction

NTLM authentication was restricted through Group Policy.

### Remote SAM restriction

`RestrictRemoteSAM` was configured so that remote SAM access was limited to administrators.

### Persistent VBS configuration

VBS / Credential Guard configuration was enforced through Group Policy with UEFI protection.

---

## Verification

After hardening, the controlled Pass-the-Hash replay attempts failed with:

```text
STATUS_NOT_SUPPORTED
```

The three tested replay mechanisms no longer succeeded against the hardened workstation.

This demonstrated that protecting LSASS alone was not considered sufficient; the project combined memory protection with network-level NTLM restrictions.

# 5. LLMNR / NBT-NS Poisoning

**MITRE ATT&CK: T1557.001**

## Principle

The initial laboratory configuration allowed LLMNR/NBT-NS name-resolution mechanisms to be tested.

The controlled poisoning scenario demonstrated that an attacker could capture NTLMv2 authentication material generated during name-resolution activity and attempt offline password recovery.

---

## Hardening

The following controls were applied:

### Disable LLMNR

LLMNR was disabled through Group Policy.

### Disable NBT-NS

NBT-NS was disabled on the relevant interfaces.

### Enable SMB signing

SMB signing was enforced to reduce the possibility of relaying captured authentication material.

### Strong passwords

Strong passwords were applied to make offline recovery of captured authentication material significantly harder.

---

## Result

The vulnerable name-resolution path was removed from the Windows clients.

The hardening therefore addressed both parts of the attack:

```text
Poisoned name resolution
          │
          ▼
Credential capture
          │
          ▼
Offline / relay abuse
```

by removing the vulnerable resolution protocols and strengthening the remaining authentication path.

# 6. Local Administrator Credential Protection with LAPS

## Objective

Local administrator password reuse creates a direct lateral-movement opportunity when the same credential or hash is available on multiple endpoints.

The project therefore deployed LAPS across the Windows clients.

---

## Configuration

The laboratory configured:

* unique local administrator passwords;
* 16-character passwords;
* upper- and lower-case characters;
* digits;
* special characters;
* automatic rotation every 30 days.

The configuration was applied to the client OU and verified through the LAPS management interface.

---

## Verification

Each Windows client received a distinct randomized local administrator password.

A previously captured local administrator NTLM hash was subsequently rejected.

This demonstrated that the old credential could no longer be reused for lateral movement after password rotation.

---

# 7. Golden Ticket and `krbtgt` Protection

## Principle

The project considered Golden Ticket persistence as the final stage of a domain-compromise chain.

A Golden Ticket can remain useful when an attacker has obtained the secret required to forge Kerberos TGTs.

The laboratory therefore included a controlled ticket-forgery scenario following domain-secret compromise.

---

## Hardening

The `krbtgt` account password was rotated twice consecutively.

The reason for the double rotation is that Active Directory maintains both the current and previous `krbtgt` secret to support ticket continuity.

A single rotation therefore does not immediately invalidate every ticket generated with the previous secret.

The second rotation removes the remaining historical secret from the effective validation path.

---

## Verification

The previously generated Golden Ticket was replayed after the two rotations.

The domain controller rejected it with:

```text
KRB_AP_ERR_BAD_INTEGRITY
```

This provided direct evidence that the previously forged ticket was no longer accepted.

# 8. ESC8 — AD CS Relay

## Principle

The project also assessed an AD CS configuration vulnerable to the ESC8 attack path.

The initial laboratory configuration exposed the AD CS web enrollment endpoint over HTTP:

```text
/certsrv/
```

This created a relay opportunity involving NTLM authentication and certificate enrollment.

The scenario was combined with domain-secret extraction and the Golden Ticket chain to demonstrate the potential impact of a compromised certificate-enrollment path.

---

## Hardening

The main remediation was to remove the unnecessary AD CS Web Enrollment component.

The vulnerable web enrollment feature was removed from the CA server.

The project also removed the vulnerable certificate template involved in the test.

---

## Verification

After remediation:

```text
/certsrv/
```

returned:

```text
HTTP/1.1 404 Not Found
```

The vulnerable certificate template was also no longer available during subsequent certificate-template enumeration.

## This removed the tested ESC8 entry point from the laboratory.

# 9. Cross-Cutting Hardening

The assessment did not rely exclusively on individual mitigations.

Two additional architectural controls were implemented.

## DNSSEC

The `nord.corp` DNS zone was signed using DNSSEC.

The configuration included:

* KSK;
* ZSK;
* RSA/SHA-256;
* NSEC3.

The objective was to provide authenticity and integrity for DNS responses and reduce DNS cache-poisoning risk.

---

## Tier Model

A Tier 0 / Tier 1 / Tier 2 administrative model was deployed.

The Active Directory structure was reorganized into separate organizational units for:

```text
Tier 0
 ├── Accounts
 ├── Computers
 ├── Groups
 └── ServiceAccounts

Tier 1
 ├── Accounts
 ├── Computers
 ├── Groups
 └── ServiceAccounts

Tier 2
 ├── Accounts
 ├── Computers
 ├── Groups
 └── ServiceAccounts
```

Dedicated administrative accounts were created for each tier.

The Tier 0 administrator was placed in the protected administrative configuration and marked as non-delegable.

The project verified that an administrative account from one tier could not simply authenticate to a system belonging to another tier.

The attacks generate Windows telemetry including authentication, Kerberos and privilege-related events.

Examples include:


as well as other host-level events depending on the technique.

# Conclusion

The Active Directory security assessment reproduced a complete controlled attack-and-remediation cycle.

The project demonstrated:

* directory reconnaissance with BloodHound;
* AS-REP Roasting;
* Kerberoasting;
* Pass-the-Hash;
* LLMNR/NBT-NS poisoning;
* local administrator credential exposure;
* Golden Ticket persistence;
* ESC8 against AD CS.

Each major scenario was followed by a corresponding hardening measure and a post-remediation verification.

The results show that the laboratory could be used both as an offensive Active Directory environment and as a source of realistic Windows telemetry for the federated intrusion-detection system.

This creates the final security loop of the project:

```text
Attack
  ↓
Telemetry
  ↓
Federated Learning
  ↓
Detection
  ↓
Hardening
  ↓
Replay
  ↓
Verification
```
